# Matthew Studio Kit (Codex)

This folder is the kit. Run every command from here as `bin/kit ...` (it uses the kit's own `.venv`, Node and HyperFrames).
`.codex/rules/kit.rules` lets `bin/kit` run outside the sandbox, because previews and renders start HyperFrames' headless
Chrome and a local Studio server. Always call it as `bin/kit`, so the rule applies.

**His own rules: `my-styles/RULES.md`.** If that file exists, read it before any edit; where it differs from this file or a
skill, it wins. When he gives you a standing rule for his videos ("always...", "never...", "from now on..."), write it
there, with the date. Never write his rules into the kit's own files (`AGENTS.md`, `skills/`, `styles/`): an update
replaces those files, and a changed one stops the update. `my-styles/` is his and is never touched by updates.

## HyperFrames' own skills: use them
`bin/kit prepare` and `bin/kit update` install HyperFrames' own skills into `~/.agents/skills`, where Codex finds them, and keep them current: `hyperframes` (read it first; its `references/` cover motion, look, overlays, captions and each kind of film), `hyperframes-cli`, `hyperframes-registry`, `media-use`, `style-sampling`, `reverse-any-video`, `slideshow`, `figma`, `remotion-to-hyperframes`. They are never a clash and are never moved away. Missing? Run `bin/kit prepare`.
- **His talking-head Shorts and YouTube videos stay on `bin/kit`**, exactly as below: draft, preview, render, check, `my-styles/RULES.md`, `my-styles/preferences.json`. On those, read the HyperFrames skills for how to build and animate a graphic (skills/graphics), and keep using `bin/kit` in place of the `npx hyperframes` commands they name.
- **Anything else** (a faceless explainer, a standalone motion graphic or title, a slideshow, a remake of a reference video, a video with no clip of him) **follows the HyperFrames skill for it directly**: start at `hyperframes`, which points to the rest (`slideshow` for a deck, `style-sampling` for an episode in a proven style, `reverse-any-video` for a remake). Give it its own folder, `.work/hf/<name>/`, and run `npx hyperframes` the way the skill says; he approves those commands when Codex asks, because the kit's rule covers only `bin/kit`. `reverse-any-video` needs a paid HyperFrames Pro login: if he isn't signed in or on Pro, tell him and stop there. `my-styles/RULES.md` still applies.
- **A faceless video that uses his voice** (a stick-figure story, an explainer over his recording): cut the voice with the kit first, every time. `bin/kit voice <his recording> --name <job>` runs the recording through the same steps as any kit video (repeated takes and pauses cut from the real sound, whole words, his pause limit, clean-up, loudness) and writes `.work/<job>/voice/voice.wav` and `words.json` (every word with its start and end on that file). Copy `voice.wav` into the HyperFrames project as its only voice, set the video's length to its length, and time every scene and on-screen word from `words.json`. Never lay his raw recording under the video: its pauses, dead air at the end and repeated takes are still in it. To drop a line, delete that piece from the job's plan and run `bin/kit voice <job>` again.

## One way to edit, every time
0. **Clips he drops into the chat** (attached videos, or a path he pastes) count the same as clips in `inbox/`: first copy each one into `inbox/` keeping its file name (`cp "<path>" inbox/`; add `-2` before the extension if that name is taken), tell him "copied to inbox", then edit the copies. "Edit these" means the ones he just dropped; "edit everything in inbox" includes them too. A reference video for the look is the exception: it never goes in `inbox/` (skills/style).
1. `bin/kit draft <clip> [--name <job>] [--long]` makes `.work/<job>/` with `edl.json` (the plan) and `TRANSCRIPT.txt`. Leave off `--style` unless he clearly named a look. The default look is already the one to use.
2. You review and fix the plan (skills/edit-short step 3, or skills/long-form). That is the only part that needs judgment.
3. `bin/kit preview <job> [<job> ...]` opens each job in its own HyperFrames Studio tab. He watches the edit live. Nothing is rendered. Give him every link. An open tab reloads by itself after a change.
   A batch (several clips, "$episode", "edit these", about 8 at a time): draft each one, then open them all with **one** `bin/kit preview` command. Number the list 1 to N in that order. Do not render while the tabs open, and do not wait on a finished mp4.
4. His notes ("on 2, cut the opener", "video 4, make the captions smaller"): apply the change, save any look preference so it sticks (skills/style), run `bin/kit preview` for that job again, and recheck quality. He can also change things by hand in Studio. Notes update the preview only. They do not render.
5. **Render only when he says so.** "render them" renders every job in the numbered list. "render 3 and 5" (or "render #3 and #5") renders those numbers only. "render <name>" renders that job. A single video: "render it". `bin/kit render <job>` renders what's in Studio, sets loudness, runs QA, and copies a PASS to `done/`. "Looks good", "finish it", and "go ahead" are not render commands.
6. A FAIL after he asked for a render: fix it from `QA-REPORT.md`, preview, and render that job again. Two fix rounds at most, then stop and report. CapCut is the other time a file gets rendered: he said "send it to CapCut".

## Rules
- **Graphics come from HyperFrames, in one theme.** Every video's graphics are built from the HyperFrames library (about 450 ready-made pieces: titles, type, lists, charts, annotations, app screens, chats, notifications, transitions) and they all wear that video's one theme, so nothing looks pasted together from different designs. Any piece may be used; none is off limits. Where a graphic goes: on a Short, in a top panel sized to it, around his full-frame face when he asks for that, or full screen; on a YouTube video, a side or inset panel or a full-screen cutaway with his face returning. Never over his face.
- **"Matthew style" is his old look, only when he asks for it.** If he says "Matthew style", "my old style", or "red captions like my old videos", edit that video with the `matthew` style (his old videos' look: white captions, crimson keywords, snap punch-ins). It applies to that video only and is never saved as a preference. Every other video stays on the default.
- **Preferences layer on top.** Small tweaks he asks for ("make my captions smaller") are saved as a preference and applied to every video after that. If saved preferences exist (`my-styles/preferences.json`), apply them automatically.
- **Just say it.** Apply the change, save the preference so it sticks, and recheck quality. Don't ask him to name a style or pick "save over / save as." If he says "copy this reference video," match that reference on top of the same default quality.
- **It must look good every time, including after Matthew's edits.** After the first draft and after every later change, look at stills of what is on screen and redo anything off. The first quality pass is not enough.
- **Use the HyperFrames library first, every time.** For each graphic: (1) `bin/kit graphics find <words>` (graphics he liked and kept); (2) `bin/kit blocks search <words>` (the whole library; search for what it should show and for the kind of piece: `headline`, `list`, `chart`, `chat`, `annotate`, `counter`, `title`); (3) install the best fit with `bin/kit blocks add <name>` and try it with `bin/kit blocks test <name>` (it prints the words and settings the piece takes). Give it his words with `"vars"`, `"data"`, or `"replace": {"its sample line": "his words"}`. If a piece is close but not right (too small on a vertical video, wrong arrangement), adjust that piece: a few lines in `graphics/_looks/<name>.css`, or `graphics/_looks/vertical/<name>.css` for vertical only. Draw a new graphic only when nothing in the library can be adjusted to fit, and then build it from library pieces where you can. Never block, wrap, or skip `hyperframes add` / `hyperframes catalog`: `bin/kit blocks` is the supported way to use them.
- **Graphics never cover his face, and the half screen isn't forced.** On a Short the default look puts a graphic in a top panel only as tall as the graphic needs, with his face right below; his face is full frame in the hook and between graphics. If he asks to keep his face full screen, set `"graphic_layout": "full"` in that video's `edl.json`: graphics then pop in around his face, or cut away full screen when there's no room. The kit places every graphic (a block on his face, in the captions, or too small to read is moved) and prints where it went. Don't fight it in `index.html`; `bin/kit check` fails a hand edit that puts a graphic on his face.
- **Captions: one size, one place.** Captions keep the same size and the same height for the whole video. A long caption breaks onto a second line instead of shrinking; they never jump while a graphic shows.
- **One theme per video.** `bin/kit draft` gives each video a theme (`"theme"` in its plan; `bin/kit theme list` shows them, and the next video gets the next one in turn). Every graphic in that video uses that theme's colours and nothing else: library pieces pick it up by themselves, and a graphic you adjust or draw uses the theme's names, never a colour of its own (`bin/kit theme show <name>`). If he asks for a different one ("make this one green"): `bin/kit theme set <theme> <job>`. If he always wants the same one, save `"theme"` in `my-styles/preferences.json`. A real app screen (iMessage, Google, ChatGPT, a notification) keeps the app's real colours and look: find a current real screenshot of that screen online, keep it in `.work/<job>/refs/`, and match it.
- **When he gives a reference video or picture, copy it with HyperFrames.** Make a contact sheet of it (`bin/kit style sheet <reel>`), then: (1) take its colours as this video's theme: write `my-styles/themes/<name>.json` with the same nine colours a kit theme has (`bin/kit theme show crimson` shows the shape) and set it on the video; (2) for each thing the reference shows (a title treatment, a list, a chat, a chart, a transition), find the closest library piece and use that; (3) adjust those pieces to match the reference instead of drawing your own. Tell him which library piece stands in for which part of the reference.
- **Message graphics: just make it up.** iMessage threads, DMs, and notifications show made-up, realistic texts from a girl, like real iMessages. Never copy or paraphrase his script into them. Put the texts in the block's `"data"`. The kit doesn't word-check them (no "mark as allowed" flag), and it stops the preview if a text copies his script or a message graphic still shows its sample or an old video's texts. **A graphic never labels itself**: no "Fictional DM", "Illustrative example", "Sample chat" or anything else that says it is made up. Give it a believable first name and the app's real header; the kit stops the preview on a label like that.
- **Every other graphic shows his words.** Every word on any other graphic comes from what he says at that moment: a quote or a close paraphrase from `TRANSCRIPT.txt`. No invented names, slogans, or claims, and never a library block's sample text. Put his words in the block's `"data"` (or `vars`, or its HTML). The kit compares each graphic's text, including words typed into its HTML, with what he says around it and stops the preview if it doesn't match.
- **Keep what he likes, and use it again.** When he says he likes a graphic (or keeps asking for the same one), keep it: `bin/kit graphics save <name> --job <job> --about "<what it shows, when to use it>"`. Later videos look there first (`bin/kit graphics find <words>`) and reuse it with `bin/kit graphics use <name> --job <job>`: same design and motion, this video's words, this video's theme. Don't save one he hasn't said he likes. A graphic made for one video lives in `.work/<job>/graphics/<name>/`.
- **Errors block preview and render.** `bin/kit preview` and `bin/kit render` run HyperFrames lint/check plus the kit's layout check and refuse to open or render with any error. Fix every error it prints (`bin/kit check <job>` shows them again), then preview again. Never open a kit job with `npx hyperframes preview` or render it with `npx hyperframes render` yourself; that skips the gate.
- **B-roll on most videos.** He wants B-roll most of the time, so add it without being asked: use what feels right for the video, usually two to four moments where a clip fits what he is saying, from his library (skills/library). Leave a moment on his face when that works better, and skip B-roll only when nothing in his library fits (say so). Fit it into the same clean layout.
- **Sound effects always, on Shorts and long videos.** The kit does it by itself: b-roll and full-screen graphics swipe in and out with a short whoosh (`"swipe": false` or `"sfx_auto": false` only when he asks for none). Small cards beside him pop in quietly. Sounds you place in the plan are kept and win. You add the rest from `library/sfx/` (`bin/kit library list --type sfx`): `ui pop` as a sent bubble appears, `ui tick` as a received one does, and any other approved sound that fits. Use only sounds in his library, never a downloaded or generated one. Keep them under his voice (about -10 to -14 dB), never two at once.
- **Resolve the editing workflow explicitly.** Start with this kit's `skills/` and `bin/kit` for kit jobs. Follow the user's explicit choice of a downloaded skill, plugin or reference. Before mixing in a different video workflow, identify its source and any conflicting instructions; do not silently import an old ColdApproach look or use another editor's defaults. For cross-computer differences run `bin/kit support doctor` and `bin/kit support inspect <job>` before changing either setup. Installed skills are candidates, not proof they were used. HyperFrames kit projects run through `bin/kit`.
- **Outside libraries update on their own.** Once a day `bin/kit` checks for newer HyperFrames and Python packages (same release line), tests them on a short clip against the current ones, and switches them in at the start of the next edit only if they pass. Never run `npm install`, `npx hyperframes upgrade` or `pip install` yourself to change versions; that skips the test. Installing library pieces with `bin/kit blocks add` is not a version change and is always fine. Pass on the one-line "kit: updated ..." notice to him.
- **Repeated takes and pauses are the kit's job.** Draft and every preview cut the first take of each restart the listener heard and any pause longer than his limit inside a kept piece (0.35 s, or `"max_pause_s"` in `my-styles/preferences.json`: `0.15` if he wants no more than 0.15 s between words), and keep graphics, b-roll and sounds on the same words. Do not put them back by merging pieces. Listen for restarts it missed (skills/edit-short). Keep a pause or both takes only when he asks (`"keep_pause": true` on the piece).
- **Whole words are the kit's job too.** A plan drafted from 2.4.3 on carries `"audio_rev": 2`: every cut follows the real sound of his recording (where each word truly starts and stops, and where the sound truly goes quiet), not the speech model's guess; the voice clean-up no longer takes the end off a piece; the ending fade starts after his last word. On such a plan never repair the voice by hand: no `audio.pre` trim to shift it, no `"end_fade_s": 0`, no re-timing every cut. If a word still sounds clipped, move that one cut edge and say which word. A plan without `"audio_rev"` is built exactly as it was, so a video he approved or one already repaired by hand does not change; to bring one over, add `"audio_rev": 2` to its plan and take the hand repairs out.
- The edit pipeline is fixed: draft, review, preview. Render and QA only when he asks ("render them", "render 3 and 5", "render <name>", "render it", or "send it to CapCut"). Never write your own ffmpeg render, caption file or render script for a video. Never edit `engine/`.
- **Preview first.** Opening Studio is not rendering. A batch of about 8 stays on previews until he names what to render. Change notes update that video's preview and stop there.
- **Hand edits stick.** Once a project's `index.html` has been changed (by him in Studio, or by you), `bin/kit preview` keeps it and says "kept (hand-edited)". Put a later plan change into `index.html` by hand, or ask him before `bin/kit preview <job> --rebuild` (it starts over from the plan and drops the hand edits).
- Do not put look values in `edl.json` except a caption height for this video. Per-video choices (cuts, keywords, which b-roll, picture or block goes where) do go there. Look preferences go in `my-styles/preferences.json` (skills/style).
- Report in plain words: the Studio link while he's reviewing; then the file in `done/`, its length, the QA verdict, and what was cut.
- **Diagnose before changing things.** If the same kit error persists after a real fix attempt, or QA fails after two fix rounds, follow `skills/support/SKILL.md`. Collect `bin/kit support doctor` and `bin/kit support inspect <job>`. When support was explicitly enabled, redacted technical records sync to that computer's private GitHub support branch. Do not reset the look, remove plugins or rebuild hand edits as a diagnostic step. Do not email or message anyone, and do not post anywhere else, automatically; the one thing that goes out is a problem report to Mitchell, as below.
- **Tell Mitchell when a result is wrong.** When he says something about a video is wrong (words cut off, a pause, captions, a graphic, timing, an update that didn't take) or the kit fails in a way you can't fix: fix it for him first, then send Mitchell a short report so the kit itself gets fixed and the same thing doesn't come back: `bin/kit report --job <job> --note "<what was wrong, in his words, and what you changed by hand>"`. It carries the kit's versions, the last commands, a few facts about the plan and that note: never his video, his transcript or a secret. If `bin/kit report --auto status` says reports go without asking, just send it. If not, show him `bin/kit report --dry-run ...` once and ask: "Want problems like this sent to Mitchell automatically from now on, so he can fix the kit?" On yes run `bin/kit report --auto on`, then send; on no, send only the ones he approves. One report per problem, not one per attempt.
